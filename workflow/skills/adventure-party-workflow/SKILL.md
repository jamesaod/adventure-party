# Adventure Party Workflow

## Recover the current state

- Work in the existing `jamesaod/adventure-party` repository. Inspect its branch, worktree, and pending commits before starting new work; preserve prepared changes when resuming a task.
- Read applicable repository instructions. Use `docs/DEVELOPMENT_WORKFLOW.md` for current branch roles and release flow, and `docs/GIT_WORKFLOW.md` for sprite integrity and transfer guidance. Prefer the explicit stable/candidate workflow over older descriptions of `main`.
- Check current repository and deployment state instead of treating a remembered revision, commit, or prior chat status as current.
- Honor the user's current scope and existing authorization. Respect pauses and rejected actions; this skill does not grant additional publishing permissions.

## Follow the established development flow

1. Fetch current `candidate` and start a scoped `feature/*` or `fix/*` branch for new work. Resume an existing prepared branch when appropriate.
2. Implement the requested change with the smallest necessary patch.
3. Run existing repository validation and relevant checks. Require **Adventure Party Validation** to pass before merging.
4. Use a pull request targeting `candidate` for ordinary development; merge through the established authorized workflow.
5. Verify the candidate deployment and the affected behavior before reporting the change as live.

- Reserve `main` for explicit milestone promotion or an explicitly requested stable hotfix. Do not promote an ordinary sprite change to `main`.
- Keep `gh-pages` generated by the publishing workflow.
- Use candidate revisions for ordinary candidate changes; obtain current numbering from the repository. Do not create a new formal R-number for every small change.
- Use the candidate QA site at `https://jamesaod.github.io/adventure-party/candidate/` and the stable site at `https://jamesaod.github.io/adventure-party/`.

## Keep sprite imports simple

Apply the user's agreed procedure:

**Selected source PNGs → 4× nearest-neighbor enlargement → `assets/sprites/` → minimal reference or metadata changes.**

1. Identify the actual user-selected source and compare it visually with the reference. Use the full archive area, catalog identity, and filename; do not infer identity from a list position or a similar name. For the selected Pool of Radiance Orc trio, read [the source mapping](references/por-orcs.md).
2. Check the source dimensions before scaling. Use 4× for the original low-resolution source; do not enlarge an already enlarged asset again. Follow newer explicit user instructions when dimensions differ.
3. Preserve source pixels, transparency, and the intended full-frame padding. Use nearest-neighbor scaling for pixel art. Do not repaint or regenerate selected artwork unless the user asks for new art.
4. Put the verified PNGs directly into `assets/sprites/`. For replacements, reuse the established asset paths and replace the relevant standing/action pair. Preserve already-correct sprites.
5. Preserve the established rendered size, anchor, footprint, alignment, and facing unless the user requests a change. Change only the metadata necessary to maintain that presentation.
6. Update only the needed asset references and cache versions. For a new role, add only its necessary registry, mapping, and role wiring. Do not change combat mechanics as part of an artwork correction.
7. Fully decode and visually inspect the resulting PNGs. Check their identity, dimensions, and transparency; successful loading alone does not prove that the correct sprite was chosen.
8. Transfer the exact verified bytes, run existing PNG-integrity validation, and check the rendered result in the candidate build. Inspect the remote state after an interrupted transfer before retrying.

Keep direct PNG assets. Do not introduce a new import pipeline or embed large image payloads into the main JavaScript file for a simple swap. Add tooling only when a concrete requirement makes it necessary.

## Keep execution proportionate and status clear

- Use small, targeted file and GitHub lookups. Reach for `rg` and specific file paths; avoid broad, large batches of code searches for a narrow sprite task.
- Keep large source files and binary/base64 payloads out of chat and tool output. Inspect the relevant snippets or concise metadata.
- Reuse existing validation instead of inventing redundant test infrastructure for a reversible asset replacement.
- Give concise progress updates. Report whether work is prepared locally, committed, pushed, merged, or verified live, and identify any actual blocker.
- When a deployment is verified, provide the playable candidate link and the brief result of the relevant visual check.
